# backlog-kanban 開発方針

## 目的・背景

プロジェクトのバックログは、backlog スキルでプロジェクトごとの Markdown ファイル (`~/.claude/backlog-data/<プロジェクト名>.md`) として管理し、複数プロジェクトの状況は pj-status スキルで確認している。

どちらも確認するたびに Claude Code を呼び、テキストの出力を読む必要がある。開発の中心である VSCode の中で、バックログの状況をカンバン形式で常に見られるようにし、確認の手間を減らすことが目的。

利用者は自分1人で、個人開発の全プロジェクトで使う。

## スコープ

### やること

- 開いているワークスペースのプロジェクトのバックログを、左から「未着手」「進行中」「完了」の3列のカンバンで、エディタ部分のタブに表示する
- 他のプロジェクトのバックログに表示を切り替える
- バックログのファイルが更新されたら、表示を自動で更新する
- WSL に接続したウィンドウと、Windows ローカルのウィンドウの両方で使えるようにする
- .vsix にまとめて、手元の VSCode にインストールする

### やらないこと

- GUI からのタスクの移動・追加・編集。バックログの書き換えは backlog スキルだけが行う
- Marketplace への公開
- git の状態 (ブランチ、未コミットの変更など) の表示 (案。pj-status スキルの役目として残す)

## 技術選定

### VSCode 拡張機能として自作する

既存のツールではなく、今の backlog スキルの書式をそのまま読む拡張機能を自作する。表示だけに絞るので、GUI での操作を Markdown に書き戻す処理が要らず、作る量が小さい。

- Trello や GitHub Projects などの外部サービスへ移行する方法は、backlog・pj-status・pr-done など、ローカルの Markdown を前提に連携しているスキルを API 経由に作り直す必要があるため採用していない
- 既存の Markdown カンバン拡張機能や Backlog.md を使う方法は、書式が backlog スキルと異なり、リポジトリ内のファイルを前提にしていて `~/.claude/backlog-data/` に全プロジェクトをまとめる置き場所と合わないため採用していない
- pj-status のようにスキルが HTML を生成して開く方法は、確認のたびに Claude Code を呼ぶ必要があり、常に開いて自動で更新される表示にならないため採用していない

### TypeScript と素の HTML/CSS

拡張機能は TypeScript で書き、Webview は素の HTML/CSS/TypeScript で作る。表示だけなら十分で、依存とビルドの設定を少なくできる。

- React や Svelte などの UI フレームワークを使う方法は、表示だけの用途にはバンドルの設定と依存が大きいため採用していない。GUI からの編集を足すことになった時点で見直す

### 配布は .vsix のみ

`vsce` で .vsix にまとめ、`code --install-extension` でインストールする。自分しか使わないため、Marketplace には公開しない。

## 設計方針

### モジュールの分け方

次の3つを分け、互いの中身に依存しないようにする。将来 GUI からの編集を足すときも、表示の部分を変えずに済むようにするため。

- データの置き場所の解決: 実行環境 (WSL / Windows) に応じて、`backlog-data` のフォルダのパスを決める
- バックログの読み込み: ファイルを読んでパースし、「プロジェクト名・3つのステータスごとのタスク一覧・解釈できなかった行」のデータにする。VSCode の API に依存しない純粋な処理にし、単体テストで確かめる
- 表示: パース結果のデータを受け取り、Webview に描く

### パース

- backlog スキルの書式 (`## 進行中` などの見出しと、`- [ ] **#004** \`優先度:高\` タイトル` の行、その下の `>` の詳細メモ) を読む
- 並び順はファイルの順をそのまま使う。backlog スキルが優先度順に並べているため、拡張機能では並べ替えない
- 書式に合わない行は黙って捨てず、「解釈できなかった行」としてデータに残し、画面に件数と内容を出す。backlog スキル側の書式が変わったときに、表示の欠けに気づけるようにするため

### プロジェクトの特定と切り替え

- 開いているワークスペースのフォルダから、pj-status と同じ順 (origin のリポジトリ名 → git のトップディレクトリ名 → ディレクトリ名) でプロジェクト名の候補を出し、`backlog-data` に該当するファイルがあれば最初に表示する
- 該当するファイルがない場合や、ワークスペースを開いていない場合は、プロジェクトの一覧から選ぶ画面を出す
- 表示中のカンバンから、`backlog-data` にある他のプロジェクトへ切り替えられるようにする
- 一覧は `backlog-data` にある `.md` のファイル全部を、名前順に並べる
- 切り替えは VSCode のクイックピックで行う。カンバンのタブのタイトルバーのボタンと、コマンドパレットのコマンド (`Backlog Kanban: プロジェクトを切り替える`) から開く。開いているフォルダのプロジェクトと表示中のプロジェクトには、説明欄に「このフォルダ」「表示中」と添える
  - カンバンの画面の中にドロップダウンを置く方法は、プロジェクトが増えたときに絞り込めないため採用していない
- 一覧から選ぶ画面では、プロジェクト名を VSCode のコマンドを呼ぶリンク (command URI) で並べる。切り替えと同じコマンドをリンクから呼ぶだけで済み、選んだ名前を Webview から拡張機能へ送るメッセージを足さずに済むため
  - 画面には案内だけ出してクイックピックを自動で開く方法は、タブを開いただけで選択リストが前に出てくるため採用していない
- 選んだプロジェクトは、カンバンのタブを閉じるまで保つ。開いたままコマンドやステータスバーから開き直したときや、自動更新のときも、選んだプロジェクトを読み直す。タブを閉じて開き直すと、開いているフォルダのプロジェクトに戻る
  - 開き直すたびに開いているフォルダのプロジェクトに戻す方法は、別のプロジェクトを見ている途中でステータスバーを押すと元に戻ってしまうため採用していない

### 実行環境ごとのデータの置き場所

バックログは WSL 側の `~/.claude/backlog-data/` にだけある。

- WSL に接続したウィンドウでは、拡張機能は WSL 側で動くので、`~/.claude/backlog-data/` をそのまま読む
- Windows ローカルのウィンドウでは、`\\wsl.localhost\<ディストリビューション>\home\<ユーザー>\.claude\backlog-data` を読む。パスは `wsl.exe --cd ~ -e wslpath -a -w .claude/backlog-data` で求める。ディストリビューションは指定せず、既定のものを使う
  - `sh -c` に引用符付きの `$HOME/...` を渡す方法は、Windows のコマンドラインで引用符が崩れて `wslpath` が引数を受け取れなかったため採用していない
  - `wsl.exe` 自身のエラーのメッセージは既定で UTF-16LE で出るため、環境変数 `WSL_UTF8=1` を付けて UTF-8 で出させる
  - WSL が止まっているときの起動を待つため、`wsl.exe` の応答は 10 秒まで待つ
  - 求めたパスはセッション中ずっと覚え、表示のたびに `wsl.exe` を呼ばない。求められなかったときは、その結果を 60 秒だけ覚える。表示のたびに `wsl.exe` を呼ばないためで、短くするのは WSL を起動したあとに開き直さずに戻れるようにするため
- 設定 `backlogKanban.backlogDir` でフォルダの絶対パスを直接指定できる。指定していれば、自動で求めたパスより優先する。自動で求められない環境 (既定以外のディストリビューションを使うなど) に備えるため
  - 設定の `scope` は `machine` にする。WSL に接続したウィンドウ (リモートの設定) と Windows ローカルのウィンドウ (ユーザーの設定) で、別々のパスを持てるようにするため。ワークスペースの設定では変えられない
- フォルダが見つからない (自動で求められない、設定のパスが相対パス・ない・フォルダでない) ときは、探した場所と理由、設定で指定できることを画面に出す
- Windows 側にバックログをコピーして読む方法は、2か所のデータがずれて古い表示になるため採用していない

### 自動更新

- `backlog-data` のフォルダを監視し、表示中のプロジェクトのファイルが変わったら読み直して描き直す
- 監視は VSCode の `createFileSystemWatcher` で、`backlog-data` 直下の `*.md` だけを対象にする。追加の依存が要らず、ワークスペースの外のフォルダも監視できるため。カンバンのタブが開いている間だけ監視する
- 描き直すきっかけは、表示している画面で分ける
  - カンバンの表示中: 表示中のファイルと、それより優先順位の高い候補のファイルの変更・作成・削除。別のプロジェクトのファイルや、優先順位の低い候補のファイルが変わっても描き直さない。一覧からプロジェクトを選んでいるときは、候補は選んだプロジェクトだけなので、表示中のファイルだけになる
  - 一覧から選ぶ画面・見つからない画面・読み込みエラーの画面: フォルダの `.md` の追加・削除・変更。増えたプロジェクトを一覧に出すため
  - 読み込みを始めてから読み終わるまでは、コマンドや切り替えのときも自動更新のときも、どのファイルの変更でも読み直す。表示中のファイルを読み込みの前のプロジェクトのままにしておくと、読み込み先のファイルの変更を取りこぼすため。自動更新でも、表示中のファイルが消えたときや開いているフォルダが変わったときは、別のプロジェクトに移ることがある
- 自動更新では、ステータスバーから開き直したときと同じプロジェクトを読む。一覧からプロジェクトを選んでいればそのプロジェクトを、選んでいなければ開いているフォルダから候補を探し直す
  - そのため、プロジェクトを選んでいないときに表示中のファイルが消え、優先順位の低い候補のファイルがあれば、そのカンバンに移る。消えたファイルを作り直すと、優先順位の高い候補のファイルとして描き直すきっかけになり、元のカンバンに戻る
  - 開いているフォルダが変わったとき (マルチルートのワークスペースで先頭のフォルダが変わったときなど) も、プロジェクトを選んでいなければ読み直す
  - 選んでいないときも表示していたプロジェクトに固定する方法は、優先順位の高い候補のファイルがあとからできても開き直すまで古い方を表示し続け、表示中のファイルが消えたあとの「見つからない」画面の候補も1件だけになり、先頭のフォルダが変わってもついてこないため採用していない
  - 表示していた候補より優先順位の低い候補へは移らずに「見つからない」画面を出す方法は、ほかの候補のファイルがあるのに「見つからない」と出て、自動更新と開き直しで結果が変わるため採用していない
- 1回の保存で変更の知らせが続けて来ることがあるため、最後の知らせから 200ms 待って1回だけ読み直す
- `backlog-data` のパスが `\\wsl.localhost\` か `\\wsl$\` で始まるとき (Windows ローカルのウィンドウで WSL 側のバックログを読むとき) は、監視の代わりに一定間隔で確かめて読み直す
  - Windows 側のファイル監視は、`\\wsl.localhost` のフォルダの変更を受け取らないため。WSL から PowerShell の FileSystemWatcher (VSCode の Windows での監視と同じ ReadDirectoryChangesW) で試したところ、Linux 側からの書き込みも Windows 側からの書き込みも通知が0件だった (Windows ローカルのフォルダでは届いた)
  - 3秒ごとに、描き直すきっかけのファイルの更新日時とサイズを確かめ、変わっていたら読み直す。一覧から選ぶ画面・見つからない画面・読み込みエラーの画面では、フォルダの `.md` の一覧と各ファイルの更新日時・サイズを比べる。backlog スキルの更新は人の操作の速さで起きるため、3秒ごとで十分すぐに見える
  - 確かめるのはカンバンのタブが見えている間だけにし、タブが前に出たときにもすぐ1回確かめる。見えていない間に 9P 越しの確認を続けないため
  - 監視に切り替えるかどうかは、プラットフォームではなくパスで決める。設定で Windows ローカルのフォルダを指定したときは監視が使えるため
  - タブが前に出たときだけ読み直す方法は、カンバンを開いたまま WSL 側で更新しても表示が変わらず、M2 の「開いたままにしておけば常に最新」が成り立たなくなるため採用していない
  - `wsl.exe` で WSL 側の `inotifywait` を動かし続けて知らせてもらう方法は、WSL に `inotify-tools` の追加が要り、動かし続けるプロセスの管理 (止まったときの起動し直しなど) も増えるため採用していない

### 描き直し

- Webview に小さなスクリプトを入れ、拡張機能から `postMessage` で送った HTML で body の中身だけを差し替える。ページを読み込み直さないため、スクロール位置が保たれる。開いていたカード (`<details>`) はタスクの ID で覚えておき、差し替えたあとに開き直す
  - 今までどおり `webview.html` を丸ごと差し替え、開閉とスクロール位置を `setState` に保存して戻す方法は、差し替えのたびに読み込み直しが入り、先頭が一瞬見えてから戻るちらつきが出るため採用していない
- スクリプトは `src/view/renderKanban.ts` の中に書き、nonce 付きの CSP で許可する。別のファイルにすると、DOM 用の tsconfig と `localResourceRoots` の設定が増えるため
- タブが隠れると VSCode は Webview を捨て、再び表示するときに最初の HTML から作り直す。そのため、作り直したスクリプトから拡張機能に知らせ、拡張機能が最新の中身を送り直す。開いていたカードとスクロール位置は `setState` に保存しておき、作り直したあとに戻す
  - `retainContextWhenHidden` で隠れている間も Webview を残す方法は、メモリを使い続け、VSCode のドキュメントでもほかの方法で済むなら使わないよう勧められているため採用していない
- 新しく開いたときとプロジェクトを切り替えたときは、読み終わるまで「読み込み中」を出す。自動更新では前の表示を残したまま差し替える。自動更新のたびに出すと画面がちらつくため
- 読み込みで予期しない例外が起きたときは、空のタブのままにせず、失敗したことと例外の内容を画面に出す
- バックログのファイルは、候補ごとに直接読み、ファイルがない (ENOENT)・フォルダだった (EISDIR) ときに次の候補へ進む。有無を確かめてから読む2段階にすると、その間にファイルが置き換わったときに読み込みエラーになるため

### 表示する場所

エディタ部分のタブ (Webview パネル) に表示する。

- サイドバー (WebviewView) に表示する方法は、幅が狭く3列が並ばないため採用していない

### カンバンを開く入口

コマンドパレットのコマンドに加えて、ステータスバーにも入口を置く。コマンドを毎回入力する手間を省くため。

- ステータスバーの左側に、アイコンと短い文字の項目を常に表示する。クリックするとコマンドパレットと同じコマンド (`backlogKanban.open`) を実行する。ツールチップはコマンド名と同じ「カンバンを開く」
  - 左側に置くのは、VSCode のガイドラインでワークスペースに関わる項目を左に置くことになっているため
- 進行中の件数などを項目に出す方法は、ステータスバーのためにバックログを読み続ける処理が要るため採用していない
- 開いているフォルダのバックログが見つかったときだけ表示する方法は、表示するかを決めるために起動時に探す処理が要り、ワークスペースを開いていないウィンドウでも一覧から選べる入口として使えなくなるため採用していない

### 見た目

- ダークモード: VSCode のテーマに追従する。色は VSCode の CSS 変数 (`--vscode-*`) から取り、拡張機能で独自の配色は持たない
- 見た目は売りではない。作り込みはせず、エディタとなじむことを優先する
- カラーテーマ: 独自のテーマは持たない
- 優先度: `高` `中` `低` のラベルをバッジで出し、テーマの CSS 変数 (`--vscode-charts-red` など) で色を付ける。`未設定` にはバッジを付けない
  - ラベルの文字だけにする方法は、ひと目で高優先度を見分けにくいため採用していない
- 列の並び: 左から「未着手」「進行中」「完了」。タスクが左から右へ流れる向きをそろえる
  - バックログのファイルの見出しの順 (進行中が先頭) に合わせる方法は、作業の流れが左右で行き来して見えるため採用していない
- 詳細メモ (`>` 行): 進行中のタスクは常に表示する。未着手・完了のタスクは、カードを開いたとき (`<details>`) だけ表示する
  - 全部の列で常に表示する方法は、完了が数十件あるプロジェクトで列が長くなるため採用していない
  - 進行中だけ表示する方法 (pj-status と同じ) は、未着手のタスクの背景を画面で見られなくなるため採用していない
- 「完了」列: 他の列と同じく、常に全件を表示する
  - 件数だけを出してクリックで展開する方法 (backlog スキルの一覧表示に合わせる案) は採用していない

### テスト

- パーサー・プロジェクト名の解決・データの置き場所の解決など、VSCode の API に依存しない処理の単体テストを、Node 標準の `node:test` で書く。`tsc` でビルドした出力に `node --test` をかけて実行する
- Extension Host を使うテストは、M1 では書かない。Webview の表示はユーザーが実機で確かめる (CLAUDE.md の「動作確認」を参照)
- ひな形の既定の `@vscode/test-cli` と Mocha は、テスト用の VSCode のダウンロードと起動が要り、WSL では表示環境も必要で遅いため採用していない。拡張機能の API を通したテストが必要になった時点で見直す
- Vitest は、純粋な処理のテストだけなら `node:test` で足り、依存パッケージが増えるため採用していない
