# backlog-kanban 開発方針

## 目的・背景

プロジェクトのバックログは、backlog スキルでプロジェクトごとの Markdown ファイル (`~/.claude/backlog-data/<プロジェクト名>.md`) として管理し、複数プロジェクトの状況は pj-status スキルで確認している。

どちらも確認するたびに Claude Code を呼び、テキストの出力を読む必要がある。開発の中心である VSCode の中で、バックログの状況をカンバン形式で常に見られるようにし、確認の手間を減らすことが目的。

利用者は自分1人で、個人開発の全プロジェクトで使う。

## スコープ

### やること

- 開いているワークスペースのプロジェクトのバックログを、左から「未着手」「進行中」「完了」の3列のカンバンで、エディタ部分のタブに表示する
- 他のプロジェクトのバックログに表示を切り替える
- バックログのファイルが更新されたら、表示を自動で更新する
- WSL に接続したウィンドウと、Windows ローカルのウィンドウの両方で使えるようにする
- .vsix にまとめて、手元の VSCode にインストールする

### やらないこと

- GUI からのタスクの移動・追加・編集。バックログの書き換えは backlog スキルだけが行う
- Marketplace への公開
- git の状態 (ブランチ、未コミットの変更など) の表示 (案。pj-status スキルの役目として残す)

## 技術選定

### VSCode 拡張機能として自作する

既存のツールではなく、今の backlog スキルの書式をそのまま読む拡張機能を自作する。表示だけに絞るので、GUI での操作を Markdown に書き戻す処理が要らず、作る量が小さい。

- Trello や GitHub Projects などの外部サービスへ移行する方法は、backlog・pj-status・pr-done など、ローカルの Markdown を前提に連携しているスキルを API 経由に作り直す必要があるため採用していない
- 既存の Markdown カンバン拡張機能や Backlog.md を使う方法は、書式が backlog スキルと異なり、リポジトリ内のファイルを前提にしていて `~/.claude/backlog-data/` に全プロジェクトをまとめる置き場所と合わないため採用していない
- pj-status のようにスキルが HTML を生成して開く方法は、確認のたびに Claude Code を呼ぶ必要があり、常に開いて自動で更新される表示にならないため採用していない

### TypeScript と素の HTML/CSS

拡張機能は TypeScript で書き、Webview は素の HTML/CSS/TypeScript で作る。表示だけなら十分で、依存とビルドの設定を少なくできる。

- React や Svelte などの UI フレームワークを使う方法は、表示だけの用途にはバンドルの設定と依存が大きいため採用していない。GUI からの編集を足すことになった時点で見直す

### 配布は .vsix のみ

`vsce` で .vsix にまとめ、`code --install-extension` でインストールする。自分しか使わないため、Marketplace には公開しない。

## 設計方針

### モジュールの分け方

次の3つを分け、互いの中身に依存しないようにする。将来 GUI からの編集を足すときも、表示の部分を変えずに済むようにするため。

- データの置き場所の解決: 実行環境 (WSL / Windows) に応じて、`backlog-data` のフォルダのパスを決める
- バックログの読み込み: ファイルを読んでパースし、「プロジェクト名・3つのステータスごとのタスク一覧・解釈できなかった行」のデータにする。VSCode の API に依存しない純粋な処理にし、単体テストで確かめる
- 表示: パース結果のデータを受け取り、Webview に描く

### パース

- backlog スキルの書式 (`## 進行中` などの見出しと、`- [ ] **#004** \`優先度:高\` タイトル` の行、その下の `>` の詳細メモ) を読む
- 並び順はファイルの順をそのまま使う。backlog スキルが優先度順に並べているため、拡張機能では並べ替えない
- 書式に合わない行は黙って捨てず、「解釈できなかった行」としてデータに残し、画面に件数と内容を出す。backlog スキル側の書式が変わったときに、表示の欠けに気づけるようにするため

### プロジェクトの特定と切り替え

- 開いているワークスペースのフォルダから、pj-status と同じ順 (origin のリポジトリ名 → git のトップディレクトリ名 → ディレクトリ名) でプロジェクト名の候補を出し、`backlog-data` に該当するファイルがあれば最初に表示する
- 該当するファイルがない場合や、ワークスペースを開いていない場合は、プロジェクトの一覧から選ぶ画面を出す
- 表示中のカンバンから、`backlog-data` にある他のプロジェクトへ切り替えられるようにする

### 実行環境ごとのデータの置き場所

バックログは WSL 側の `~/.claude/backlog-data/` にだけある。

- WSL に接続したウィンドウでは、拡張機能は WSL 側で動くので、`~/.claude/backlog-data/` をそのまま読む
- Windows ローカルのウィンドウでは、`\\wsl.localhost\<ディストリビューション>\home\<ユーザー>\.claude\backlog-data` を読む。パスは `wsl.exe` で WSL 側の `wslpath -w` を呼んで求める案。求めたパスはセッション中は覚えておき、表示のたびに `wsl.exe` を呼ばない
- 自動で求められない環境に備えて、設定でフォルダのパスを直接指定できるようにする
- Windows 側にバックログをコピーして読む方法は、2か所のデータがずれて古い表示になるため採用していない

### 自動更新

- `backlog-data` のフォルダを監視し、表示中のプロジェクトのファイルが変わったら読み直して描き直す
- `\\wsl.localhost` 越しの監視は変更を取りこぼすことがあるため、Windows ローカルのウィンドウでの方式は M3 の着手前に決める (未決事項を参照)

### 表示する場所

エディタ部分のタブ (Webview パネル) に表示する。

- サイドバー (WebviewView) に表示する方法は、幅が狭く3列が並ばないため採用していない

### カンバンを開く入口

コマンドパレットのコマンドに加えて、ステータスバーにも入口を置く。コマンドを毎回入力する手間を省くため。

- ステータスバーの左側に、アイコンと短い文字の項目を常に表示する。クリックするとコマンドパレットと同じコマンド (`backlogKanban.open`) を実行する。ツールチップはコマンド名と同じ「カンバンを開く」
  - 左側に置くのは、VSCode のガイドラインでワークスペースに関わる項目を左に置くことになっているため
- 進行中の件数などを項目に出す方法は、ステータスバーのためにバックログを読み続ける処理が要るため採用していない
- 開いているフォルダのバックログが見つかったときだけ表示する方法は、表示するかを決めるために起動時に探す処理が要り、ワークスペースを開いていないウィンドウでも一覧から選べる入口として使えなくなるため採用していない

### 見た目

- ダークモード: VSCode のテーマに追従する。色は VSCode の CSS 変数 (`--vscode-*`) から取り、拡張機能で独自の配色は持たない
- 見た目は売りではない。作り込みはせず、エディタとなじむことを優先する
- カラーテーマ: 独自のテーマは持たない
- 優先度: `高` `中` `低` のラベルをバッジで出し、テーマの CSS 変数 (`--vscode-charts-red` など) で色を付ける。`未設定` にはバッジを付けない
  - ラベルの文字だけにする方法は、ひと目で高優先度を見分けにくいため採用していない
- 列の並び: 左から「未着手」「進行中」「完了」。タスクが左から右へ流れる向きをそろえる
  - バックログのファイルの見出しの順 (進行中が先頭) に合わせる方法は、作業の流れが左右で行き来して見えるため採用していない
- 詳細メモ (`>` 行): 進行中のタスクは常に表示する。未着手・完了のタスクは、カードを開いたとき (`<details>`) だけ表示する
  - 全部の列で常に表示する方法は、完了が数十件あるプロジェクトで列が長くなるため採用していない
  - 進行中だけ表示する方法 (pj-status と同じ) は、未着手のタスクの背景を画面で見られなくなるため採用していない
- 「完了」列: 他の列と同じく、常に全件を表示する
  - 件数だけを出してクリックで展開する方法 (backlog スキルの一覧表示に合わせる案) は採用していない

### テスト

- パーサー・プロジェクト名の解決・データの置き場所の解決など、VSCode の API に依存しない処理の単体テストを、Node 標準の `node:test` で書く。`tsc` でビルドした出力に `node --test` をかけて実行する
- Extension Host を使うテストは、M1 では書かない。Webview の表示はユーザーが実機で確かめる (CLAUDE.md の「動作確認」を参照)
- ひな形の既定の `@vscode/test-cli` と Mocha は、テスト用の VSCode のダウンロードと起動が要り、WSL では表示環境も必要で遅いため採用していない。拡張機能の API を通したテストが必要になった時点で見直す
- Vitest は、純粋な処理のテストだけなら `node:test` で足り、依存パッケージが増えるため採用していない

### 判断の記録

ここに書いた「採用していない」方法に加えて、不具合の修正で選んだ方式も、同じ形で該当する項目の下に追記していく。
